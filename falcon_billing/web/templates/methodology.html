Classification & Billing Methodology

How sensors are collected, classified into license types, and averaged for billing.

Step 1: Hourly Sensor Collection

Every clock hour, four NGSIEM queries run against the Falcon data lake:

Query What it finds License type
Total sensors SensorHeartbeat (not pods), anti-joined with OCI container events FCS + EPP pool
Container hosts (FCSC) AIDs with OciContainerStarted / OciContainerTelemetry events FCSC
Pods (FMC) SensorHeartbeat with ProductType=Pod FMC
FCS candidates Total minus FCSC minus FMC (anti-join) FCS or EPP (needs classification)

Each query returns a set of unique AIDs (Agent IDs) active in that hour.

Step 2: FCS vs EPP Classification

For sensors in the FCS candidate pool, the Hosts API provides metadata used to classify each host into the appropriate license type based on its infrastructure characteristics.

Priority Signal Logic
1 (highest) system_manufacturer is a hypervisor VMware, QEMU, KVM, Xen, Hyper-V, VirtualBox, Nutanix → FCS
2 cloud_provider (IMDS) AWS, Azure, GCP, OCI, Alibaba, etc. → FCS
3 system_manufacturer is a cloud vendor Amazon, Google, Alibaba Cloud, etc. → FCS
4 product_type_desc Server, Domain Controller → FCS (bare-metal server)
5 sensor_tags (fallback) Tags containing aws, azure, cloud, vm, vdi → FCS
6 (default) None of the above → EPP (physical workstation, laptop, mobile)

Why hypervisor manufacturer is #1

A Linux workstation on VMware is still a VM (VDI) — it should be FCS regardless of product_type_desc. Physical workstations (Dell, HP, Lenovo, Apple) correctly fall through to EPP.

Step 3: Hourly Count Storage

Each clock hour produces one row in hourly_counts:

Column Meaning
unique_sensor_countTotal distinct AIDs active in this hour
fcs_countFCS-classified sensors (VMs, servers)
epp_countEPP-classified sensors (endpoints)
fcsc_countContainer host sensors
fmc_countPod sensors (managed containers)

Invariant: fcs_count + epp_count + fcsc_count + fmc_count = unique_sensor_count

Step 4: License Averaging

FCS / FCSC / FMC

28-day hourly average

SUM(hourly counts over 672 hours) ÷ 672

Rolling window — slides forward each hour. VMs that scale down at night reduce the average.

EPP

7-day weekly average

SUM(daily peak EPP counts over 7 days) ÷ 7

Daily peak = max EPP sensors seen in any hour that day. Averaged over 7 days.

Hourly Averaging vs Weekly Averaging

Workload Pattern EPP Count (weekly avg) FCS Count (hourly avg) Reduction
Always-on VMs (24/7) 100 100 0%
Business hours only (12h/day) 100 50 50%
Dev/test (weekdays 9-5) 100 24 76%
Auto-scaling (40-60% peak) 100 40-60 40-60%
CI/CD runners (ephemeral) 50 5-15 70-90%

EPP weekly average counts every sensor seen in a day as 1 for that day. FCS hourly average only counts a sensor in the hours it was actually active. Ephemeral and auto-scaling workloads benefit most from hourly averaging.

License Type Reference

FCS — Cloud Security

Covers: Cloud VMs, on-prem VMs (VMware, Hyper-V, KVM), VDI, bare-metal servers

Metering: 28-day hourly average

Signal: Hypervisor manufacturer, cloud provider, or server role

EPP — Endpoint Protection

Covers: Physical workstations, laptops, mobile devices

Metering: 7-day weekly average of daily peaks

Signal: Physical manufacturer (Dell, HP, Lenovo, Apple) + no hypervisor indicators

FCSC — Container Hosts

Covers: Hosts running OCI containers (K8s nodes, Docker hosts, ECS instances)

Metering: 28-day hourly average

Signal: OciContainerStarted / OciContainerTelemetry events in NGSIEM

FMC — Managed Containers

Covers: Kubernetes pods, Fargate tasks, serverless containers

Metering: 28-day hourly average

Signal: SensorHeartbeat with ProductType=Pod
